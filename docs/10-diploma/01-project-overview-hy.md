# 01 — Costly․ նախագծի ընդհանուր նկարագիր

> Ստուգված վիճակ՝ **2026-11-19**, Asia/Yerevan։ Կոդի հիմք՝ `main`, commit `248edd60e8429934391d8d2d49fd11eaf778aded`։ Այս փաստաթուղթը նկարագրում է և՛ ներկայիս արդյունքը, և՛ դիպլոմային աշխատանքի նպատակը՝ դրանք հստակ տարբերակելով։

## Դիպլոմային աշխատանքի թեման

**«Անձնական ֆինանսների կառավարման, վերլուծության և կանխատեսման համակարգի մշակում»**։

Costly-ն անձնական ֆինանսների web application է։ Դրա վերջնական նպատակը մարդու սեփական ֆինանսական պատմությունը օգտագործելն է՝ ծախսերը հասկանալու, ապագա մնացորդները գնահատելու և խնայողության նպատակների վրա որոշումների ազդեցությունը հաշվարկելու համար։

Ներկայում իրականացված է այս շղթայի հաշվառման հիմքը՝ գրանցում և մուտք, հաշիվներ, կատեգորիաների API, եկամուտներ ու ծախսեր, ընթացիկ մնացորդներ։ Վերլուծությունը, կանխատեսումը և որոշումների աջակցությունը **նախագծված են, բայց դեռ իրականացված չեն**։

```text
Գրանցել → Հասկանալ → Կանխատեսել → Որոշել
Ledger    Analytics   Forecasting   Goals / What-if / Insights
առկա      ապագա       ապագա         ապագա
```

## Խնդիրը և արդիականությունը

Եկամուտների և ծախսերի ցուցակը պատասխանում է «ինչքա՞ն գումար եմ ծախսել» հարցին։ Սակայն ֆինանսական պլանավորման համար անհրաժեշտ են նաև այլ պատասխաններ․

- արդյո՞ք այս ամսվա ծախսը սովորականից մեծ է,
- որքան գումար կարող է մնալ ամսվա վերջում,
- արդյո՞ք խնայողության նպատակը հասանելի է ընթացիկ վարքագծով,
- ինչպե՞ս կփոխվի նպատակի ժամկետը նոր գնումից կամ ծախսի կրճատումից։

Costly-ի նախագծային տարբերակիչ գաղափարը **goal-aware decision support**-ն է․ խորհուրդը պետք է կապվի չափելի ազդեցության հետ, օրինակ՝ տարեկան խնայողության և նպատակի ժամկետի փոփոխության։ Սա ակնկալվող արդյունք է, ոչ ներկայիս ծրագրի ցուցադրելի հնարավորություն։ Այս փաստաթուղթը նաև չի պնդում, թե շուկայում այլ համակարգերը նման հնարավորություններ չունեն․ համեմատական ուսումնասիրությունը պահանջում է առանձին աղբյուրներ։

## Օգտատերը և գործածության սցենարը

Հիմնական թիրախը AMD-ով եկամուտ ստացող անհատն է, որը ցանկանում է վերահսկել առօրյա ծախսերը և ունենալ մեկ կամ երկու խնայողության նպատակ։ «Single-user personal finance» ձևակերպումն այստեղ նշանակում է անձնական, ոչ համատեղ ընտանեկան հաշվառում։ Backend-ը պահում է բազմաթիվ գրանցված օգտատերեր, որոնց տվյալները պետք է մեկուսացված լինեն։

**Այսօր հնարավոր սցենար․** օգտատերը գրանցվում է, ստեղծում բանկային կամ կանխիկ հաշիվ, գրանցում եկամուտ և ծախս, ֆիլտրում գրառումները, ուղղում սխալը և տեսնում վերանայված մնացորդը։

**Ապագա սցենար․** ներմուծում է մի քանի ամսվա պատմություն, ստանում ծախսերի baseline, կանխատեսում և համեմատում գնման երկու տարբերակի ազդեցությունը իր խնայողության նպատակի վրա։

## Նպատակն ու խնդիրները

Ընդհանուր նպատակը տեղային աշխատող, բացատրելի և փորձարկելի համակարգ կառուցելն է։ Աշխատանքը բաժանվում է հետևյալ խնդիրների․

1. Ճշգրիտ ֆինանսական domain model՝ գումար, հաշիվ, կատեգորիա, գործարք և ամսաթիվ։
2. Authentication, տվյալների մեկուսացում և տվյալների բազայի consistency։
3. Հարմար web client՝ վավերացում, սխալների հասկանալի հաղորդագրություններ և responsive layout։
4. **Ապագայում՝** ներմուծում, recurring payments, budgets և goals։
5. **Ապագայում՝** descriptive statistics, anomaly detection և պարզ time-series forecasting։
6. **Ապագայում՝** deterministic what-if simulation և կանոնահեն recommendations։
7. Յուրաքանչյուր փուլի համար կոդ, թեստեր, փաստաթղթեր և վերարտադրելի ստուգումներ։

## Շրջանակը և սահմանափակումները

Ներկայիս տարբերակն օգտագործում է AMD։ Գումարները պահվում են integer minor units-ով, API-ում փոխանցվում են decimal string-երով։ Աջակցվում են դրական income/expense amounts և նաև բացասական account opening balance։ Առանձին account type `credit_card` ունենալը չի նշանակում վարկային պայմանագրերի կամ տոկոսների հաշվառման համակարգ ունենալ։

Դեռ չկան transfers, merchants, recurring rules, statement import, dashboard totals, budgets, goals, analytics, forecasts, what-if, insights և AI assistant։ Դրանցից շատերը հաստատված ապագա ծավալի մաս են, բայց չեն մտնում Transactions MVP-ի մեջ։

Native iOS/Android client-ը [ADR-0011](../03-architecture/adr/0011-native-mobile-clients.md)-ում ունի **Proposed** կարգավիճակ։ Փաստաթղթի merge-ը հավասար չէ առաջարկի ընդունմանը կամ mobile app-ի ստեղծմանը։ Հայերեն այս նյութերը նույնպես չեն նշանակում, որ ծրագրի UI-ն արդեն հայերեն է։

Հիմնական շրջանակից դուրս են bank integrations, investments/crypto, household sharing, OCR, microservices, Kubernetes և բարդ ML models։ Optional AI explanation-ը անհրաժեշտ չէ դիպլոմի ամբողջական լինելու համար։
