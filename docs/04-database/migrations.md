# Database migrations

Costly uses Prisma 7 migrations for the schema (ADR-0003). This page covers how to run them and
how they reach tests and CI.

## Files

| Path | Purpose |
|---|---|
| `apps/api/prisma/schema.prisma` | Generator and datasource. Domain models are added by the module that owns them. |
| `apps/api/prisma/migrations/` | Committed SQL migrations, created by `migrate dev`, plus Prisma's `migration_lock.toml`. |
| `apps/api/prisma7.config.ts` | CLI configuration. `prisma7.config.*` is the file name Prisma 7.10 looks for first. `prisma.config.*` is its legacy name. |
| `apps/api/src/generated/prisma/` | Generated client. Git-ignored and regenerated by `postinstall`. |

The CLI reads `DATABASE_URL` through `prisma7.config.ts`, which loads `apps/api/.env`. The running
API doesn't use that file. It gets the URL from the validated `ConfigService`.

## Commands

Run these from the repository root after `pnpm infra:up`, with `apps/api/.env` copied from
`apps/api/.env.example`.

| Command | When |
|---|---|
| `pnpm db:generate` | Regenerate the client after editing the schema. `pnpm install` already does this. |
| `pnpm db:migrate` | **Development only.** Diffs the schema against the database, writes a new migration under `prisma/migrations/` and applies it. Interactive: it can ask to reset the database. |
| `pnpm db:deploy` | Applies committed migrations that haven't run yet. Never creates migrations and never prompts. Used by tests and anywhere else that isn't a developer's machine. |

## Workflow for a schema change

1. Edit `schema.prisma` in the same change as the module that owns the tables.
2. Run `pnpm db:migrate`, using a descriptive name such as `add_users`.
3. Read the generated `migration.sql`. Constraints that Prisma can't express, such as `CHECK`
   or partial unique indexes, get added to that SQL by hand before committing.
4. Commit the schema, the migration folder and the code that uses them together.

An applied migration is never edited. Corrections go in a new migration.

## Tests and CI

The API integration tests start a throwaway PostgreSQL container and run
`prisma migrate deploy` against it before the application boots
(`apps/api/test/health.e2e.spec.ts`). Every committed migration is therefore applied on each
`pnpm test`, locally and in CI. `apps/api/test/users.schema.spec.ts` uses the same helper
(`test/support/migrations.ts`) to test the schema itself.
